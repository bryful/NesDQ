# FF2 調査記録

**2026-10-26：ユーザーの指示により解析を再開し、BGM・主要SEの等速化を通常版へ組み込んだ。優先順位は戦闘 → ダンジョン → フィールド → その他。使用頻度の低い処理は変更を抑える。通常版の接続は `app/ff_audio.inc`、未完のイベント記録再生実験は `tools/experimental/ff2_core_bridge.c` に分離している。現行仕様は `docs/ff-input.md`、組込みと検証は `docs/ff-audio.md` を参照。以下は前回の実験記録。**

現在は通常の1倍速で動作。等速音声を伴う倍速は準備中で、Speedは無効。

## 確認した入力

Mapper 2での実行を確認した。

`--check` で1320フレームの実行、音声生成、通常セーブ、5枠のステート保存復元を確認。全ゲーム進行やAndroid実機での確認ではない。

## 音声の接続候補

16 KiB単位のPRG bank 13にBGM更新ルーチン `$9800` がある。固定bank 15の `$C746`／`$C74F` から切り替えて呼ぶ。要求はゼロページ `$E0`、音声作業領域はゼロページ `$B0` 以降と `$6F00` 周辺。`$E0` の上位ビットは更新要求の判定に使用される。

効果音には別経路がある。固定bankの `$C921` などはAPUの矩形波2へ直接書き込み、`$E5` で継続時間を管理する。bank 3の戦闘処理にもノイズ等への直接書き込みが複数ある。DQ3のように曲番号だけを音声用コアへ転送する方法では、これらの効果音を再現できない。

`$FA00` は汎用のbank間呼出につながる処理であり、BGM開始APIとして使用しない。元ROMファイルは変更していない。

次の作業は、BGM更新の単独実行と、戦闘・メニュー・移動中の各効果音の入口および時間管理を照合すること。音声と入力補正の検証が揃ってから倍速を有効にする。

## 検証用コアの実装

内部プロファイル22を追加した。アプリのROM認識にはまだ登録しておらず、通常版のFF2は引き続き1倍速で動く。

- `$E0` のBGM要求を音声用コアへ転送。bank 13のドライバー自身による状態更新は転送しない。
- bank 5の `$BA03` が戦闘用SEの開始、`$BA00` が更新。開始要求は `$6F60` への書込で捕捉する。
- 固定bankの `$DB2E`・`$DB45`、`$C921` の矩形波SEを接続。
- `$DE67` のエラー音は16回のVBlank待ちを含む。NMI内で音声処理を実行せず、音声用コアの通常ループから元の `$FE00` 待機を呼び、NMIは原作のRAM `$0100` へ渡す。この待機中のステート復元も検証した。
- 名前入力等の共通メニューはbank 14の `$9693`。同方向の長押し時、`$47` の更新間隔を実時間へ合わせ、待機回は元の「入力なし」の出口へ戻す。通常の押下状態は維持する。補正の途中状態は既存スナップショットの予約フィールドへ保存する。
- もう一つの入力処理 `$FC34` の待ちカウンター `$36` もスケーリングする。こちらの長時間プレイは未検証。

6502の書込フィルターに渡るPCはオペランド読取後である。例として `$DB42: STA $E5` はPC `$DB44` で捕捉する。

接続コードは `tools/generate_ff2_harness.py` から `app/ff2_harness.h` を生成する。配布ROMの書換えや、アプリ実行時のPython使用はない。

確認結果:

- 通常ゲームの開始・名前入力まで3300フレームで13件の要求を捕捉。分離音声のエネルギー20662.4、ゲーム音声20744.9（差約0.40%）。波形の完全一致を示すものではない。
- BGM・矩形波SE・戦闘SE・待機を含むSEの同一要求列で、ゲーム側を1〜6倍にしても239616音声サンプルが完全一致。
- BGM表31項目、戦闘SE表33項目を各240フレーム、停止・不正音声値・要求残留なしで実行。各項目の全曲・全SEを最後まで確認したという意味ではない。
- 名前入力画面で上下を長押し・離す操作を繰り返し、1〜6倍のカーソル変化がホストフレーム `0,17,30,47,60,77,90,107` で一致。長押し途中のステート復元後も映像が一致。
- 診断用リプレイで名前入力と冒頭のイベントを経て町の画面へ到達。名前は検証用で、実ユーザーの保存データは使わない。

```powershell
cmake --build build --config Release --target nesdq_ff2_check nesdq_ff2_input_check nesdq_ff2_probe -- /p:PreferredToolArchitecture=x64 /m
.\build\Release\nesdq_ff2_check.exe .rom/game.nes
.\build\Release\nesdq_ff2_input_check.exe .rom/game.nes
.\build\Release\nesdq_ff2_probe.exe .rom/game.nes 9000 tests/replays/ff2-probe.txt build/ff2-probe
python tools/generate_ff2_harness.py
```

診断リプレイの各行は「開始フレーム・終了フレーム（含まない）・NESボタンマスク」。APU書込通知はシリアライズ対象外で、FF2プロファイル22で音声要求の捕捉に利用する。trace 2では診断ログも出力する。その他のゲームでは通知を設定しない。

## 有効化前の残作業

bank 3のイベント専用の直接APU操作を確認し、原作と同じ時間で再生する経路へ接続する。これらを単純に高速転送するとSEが短くなるため、現在のドライバー接続だけで「全効果音対応」とは扱わない。その後、アプリのROM認識・音声用ベクター・統合ステート検証へ登録し、Android実機で確認する。

## 地形音・扉音・ミュート

地形音の原作処理は固定bank `$C130`（水面側）と `$C13D`（もう一方のノイズ変調）。原作の `$F0` を使うため、音声用コアに独立した位相 `$04FB` と種別 `$04FC` を持つ。同じ種別の通知が連続した場合、ゲーム側の高速な位相を採用せず、音声フレームごとに1回進める。切替時には通知に含めた元の位相を採用する。戦闘SE開始や扉音、明示ミュート時には連続音を停止する。

`app/ff2_sound_rom.hpp` は音声用コピーだけの `$C156`（地形音の末尾）と `$C8DF`（扉音の末尾）をRTSへ変更する。これらの処理は元々ゲームループや入力処理へ続くため、音源への書込が終わったところで音声コアへ戻す。元の命令列とサイズを確認してから変更し、ゲーム用ROM・ディスク上のROMには触れない。

`$D913` のチャンネルミュートと `$C4A0` の全音停止も元ルーチンを呼ぶ。原作の停止をBGM更新で直ちに上書きしないよう、フレーム内のBGM・SE更新後に適用する。ノイズだけの停止も独立して扱う。

追加検証:

- `python tools/check_ff2_environment.py .rom/game.nes`：別の6502実装py65で原作と接続コードの音源レジスター書込を比較。地形音2種類×256位相、扉音、2種類の全体ミュートが一致。
- ネイティブ側でも、地形音・扉音・ミュートを含めた要求列で1〜6倍の音声239616サンプルが一致。
- 地形通知の位相を毎回6ずつ増やしても、再生側の位相は毎音声フレーム1ずつ進む。連続再生中のステート復元後も音声が一致。
- 開始・名前入力3300フレームの比較は20要求、分離音声エネルギー20646.9、ゲーム20744.9（差約0.47%）。完全な波形一致や全場面での確認を意味しない。

地形を離れる場面やイベントとの重なりは、引き続き実ゲームで確認する必要がある。

## 原作の音声更新頻度

9000フレームの診断リプレイで、BGM更新があるフレームは7732。そのうち1回更新が7724フレーム、2回更新が8フレームで、その他のフレームでは更新しない。常に1回更新すると、イベントや画面切替の待機中にもドライバーの楽譜を進めてしまう。

ソース側でBGM `$9800` と、動作中SEの `$BA6F` の実行回数をフレームごとに数える。`wiiz_core_sound_clock` で音声コアへBGM・SEの更新回数を別々に渡せるようにした。原作との1倍比較を行う診断ツールと検証プログラムではこの回数を使う。停止中もAPU自体の時間は進め、楽譜・SEシーケンサーだけを止める。単独音声検査の既定値は従来通り各1回。

更新回数・待機状態は音声コアのRAM `$04F7`〜`$04F9` に置くため、既存ステートの仕組みで保存される。ソース側の回数カウンターは完了した直近フレームの計測値であり、次のフレーム開始時にリセットする。

追加検証:

- 2回更新×10フレームと1回更新×20フレームで、音声ドライバーの作業RAMが一致。
- 更新回数0の間は作業RAMが変化せず、停止中の保存復元でも出力音声が完全一致。
- 更新頻度対応後の開始・名前入力3300フレーム比較は、分離音声20518.1・ゲーム20744.9。音源の位相や書込タイミングが異なるため、エネルギーだけで音声の一致を判定しない。
- イベントを含む9000フレームは要求転送・音声用コアとも停止せず完走。短区間のエネルギー差は残り、切替要求・レジスター系列の照合が必要。
- Windows本体・診断ツールとAndroid arm64 Debugのビルド、およびDQ3／DQ4の通常・倍速ステート回帰検査が成功。

アプリへの統合時には、高速側の複数フレームから音声側の等速更新を決める処理も必要。FF2の倍速が通常版へ有効化済みという意味ではない。
