# FF2・FF3の倍速と入力補正

2026-10-26に等速音声を通常版へ組み込んだ。対応範囲と検証は `ff-audio.md` を参照。

0.4.0ではゲーム速度に連動する音声を使用していた。現在はBGM・主要SEを別の音声用コアで等速再生する。入力補正は維持する。

## 入力プロファイル

| 作品 | 入力プロファイル |
| --- | --- |
| FF2 | 122 |
| FF3 | 123 |

原作の命令・入力処理の位置に依存するため、内容が一致したROMだけで補正する。ROMファイルやゲーム用ROMの命令列は変更しない。

## 補正箇所

FF2の共通メニューは16 KiB PRG bank 14の `$9693`、FF3はbank 30の `$9175`。どちらも `$A1` で同方向を検出し、`$47` のカウンターでリピートを決める。カウンターを進める間隔と、再び入力を返すまでの1フレームを実時間に合わせる。待機回は元ルーチンの「入力なし」の出口へ戻す。押下状態そのものは維持する。

別系統の入力処理はFF2 `$FC34` の `$36`、FF3 `$FBAA` の `$14` の待ち時間を補正する。速度変更時には残り時間を換算する。補正途中の状態は既存のネイティブステートの予約フィールドで保存する。

同じRAM番地が別用途で使われている間は、速度変更で書き換えない。最後の書込が対象の入力ルーチンによるものか追跡し、その状態も予約フィールドのbit 16に保存する。起動直後の入力処理が未使用の場面で、速度を変えても全RAMが不変であることを検査する。

名前入力での基準となるカーソル変更フレーム:

- FF2：`0,17,30,47,60,77,90,107`
- FF3：`0,17,19,30,47,49,60,77,79,90,107,109`

上下を20ホストフレーム保持し、10フレーム離す操作で、1〜6倍すべてが基準と同じ変更時刻・順序になることを確認する。左右の保持も含め、入力途中のステート復元後に映像が一致する。

## 音声・保存

ゲーム側はホスト更新ごとに1〜6フレーム、音声側は1フレーム進む。高速側で発生した要求を順番に転送する。音声のサンプルレートや音程を変えて等速化しない。1倍速の起動直後はゲーム側の音声を使い、倍速へ切り替えた後は音声用コアの出力を使い続ける。

FFの新規ステートは既存の `NESDQST2` にゲーム・音声用両コアを保存する。0.4.0のフラグ2と8バイトの音声変換状態、0.3.2のフラグ0、旧ネイティブ形式も読み込める。音声用コアがない旧ステートは現在BGMを先頭から再開する。新規FFステートは旧アプリでは読み込めない。DQの形式・サイズは維持する。

検証コマンド:

```powershell
cmake --build build --config Release --target nesdq nesdq_ff_input_check -- /p:PreferredToolArchitecture=x64 /m
.\build\Release\nesdq_ff_input_check.exe .rom/game.nes
.\build\Release\nesdq_ff_input_check.exe .rom/game.nes
.\build\Release\nesdq.exe --check .rom/game.nes build/checks/ff2
.\build\Release\nesdq.exe --check .rom/game.nes build/checks/ff3
```

`--check` は2〜6倍の映像・音声を含むステート再実行、5スロット、SRAM、旧形式の読込、不正チェックサムで実行中ゲームを差し替えないことを検査する。全場面の入力やAndroid実機での検証を意味しない。

0.4.0では両作品の入力検査と `--check` が成功。実際に0.3.2で作成したFF2のステートもSDLの読込操作で確認した。Windows上のdummy音声・描画を使った6倍の各6秒計測では音声不足0、50ms超のフレーム0。Android arm64 Debugはビルドを確認し、実機操作は未確認。
