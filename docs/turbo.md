# DQ4の倍速と等速音声

## 対象と既存実装

対象は内容を照合したDQ4。完全一致するPRGの二重収録はメモリ上で正規化する。元のROMファイルは変更しない。対象外にはROM固有の接続を適用しない。

Wiizの音声専用binjnes方式と既存のRAM書込コールバックを再利用する。binjnesのCPU・PPU・APU・MMC1、音声ドライバー・音楽・SEのデータは既存のものを利用し、エミュレーターと音源を新規実装しない。上流ソースには追加変更をしていない。独自部分はROM固有の呼出し監視、音声専用コアを起動する接続コード、UI・保存との接続。

## DQ4で確認した呼出し

- 固定PRGバンク31の `$E685` が音声の定期更新。
- `$EF59` が通常の音楽・SE要求、`$F05C` が別モードの音楽要求、`$F055` がフェード、`$EED3` が音量設定、`$F088` が初期化。
- 通常・別モードの要求は `$F078` でAをスタックに保存する。`$BF` への書込時（PC `$F07F`）にスタック上の戻り先 `$EF5B`／`$F05E` を確認し、保存された要求値を取得する。
- `$BB` 書込のPC `$F05B`／`$F0A8` でフェード／初期化、`$B0` 書込のPC `$EEDF` で音量要求を取得する。ドライバー自身の通常更新は要求として転送しない。

これらは手元のROMを静的に逆アセンブルし、binjnes実行中の呼出しを照合したもの。

## 実行

ゲーム用コアをホスト更新ごとに1〜6フレーム動かし、最後の画面を表示する。ゲーム側の音声生成は通常どおり続ける。
音声専用コアはホスト更新ごとに1フレームだけ動かす。要求を順序どおりに渡し、既存APUで生成した音声を使う。音声の間引き・サンプルレート変更で等速化しない。

音声専用ROMのメモリコピーでは割り込みベクターだけを接続コードへ向ける。起動コードはCPU RAM `$0700`、NMIは `$0780`、要求転送は `$0680–$06FD`。音声ルーチンとデータは元ROMのものを呼ぶ。コードの生成元は `tools/generate_dq4_harness.py`。元ROMとゲーム側の実行ROMは変更しない。

1倍速での起動時は従来のゲーム側の音声を出す。音声専用側も要求を受けて進めるため、倍速への切替時に音楽を先頭から再開しない。いったん倍速へ切り替えた後は、1倍へ戻しても音声専用側を使う。

1ホスト更新の要求キューは最大42件。上限を越えた場合は停止してエラーを出し、黙って要求を落とさない。

## 入力

物理的に押しているボタンの状態を、1倍速と同様にそのまま既存コアへ渡す。一度のストローブだけへ短縮しない。DQ4は長押しを複数回読み直すため、短いパルスへ変換すると方向入力を失う。

原作の共通メニュー処理（PRG16 KiBバンク18）に限り、`$03CD` のリピート期限を書き込むPC `$BCEB` で、原作の待ち時間12／6フレームを速度倍する。`$03E2` のPC `$BD06` の15フレーム期限も速度に合わせる。基準のフレームカウンターは `$050C`。スピード切替時は残り時間を換算し、長押し中のステートには補正速度も保存する。
原作が入力を消費する順序と、方向・A/B/Select/Startの長押し状態を保つ。1倍速では期限を書き換えない。

## ステート

新形式NESDQST2はゲーム・音声専用コアの両スナップショット、要求キュー、速度、音声経路、元ROMの識別子、SHA-256チェックサムを保存する。binjnesとWiizの既存シリアライザー・音声バッファ復元を再利用する。読込は別のコアへ検証してから差し替える。
旧形式のゲーム単独ステートは読み込める。等速音声用の状態がないため、必要なら現在BGMを先頭から再生する。

## 検証と限界

- 1〜6倍、ホスト300更新。ゲームは300〜1800フレーム進行し、参照コアの画面と一致。
- 同じタイミングのBGM・SE・フェード要求を音声専用側へ与えた場合、全速度で239616サンプルが完全一致。
- 0.2.1で上下左右の長押しを全速度で検証。ゲームが読み取った `$14` が実際の押下状態を保持することを確認。
- 冒険の書選択画面のカーソル位置 `$03CF` を観測し、上下の8回の移動とリピート間隔が1倍速と最大1ホスト更新の差で一致。長押し途中のステート復元後の画面も完全一致。
- 旧版の「ストローブ受付19回」は入力コールバック内のカウンターであり、ゲームが方向入力を消費できた証拠になっていなかった。この検査を廃止し、実際のゲーム側の値とカーソル移動を検証する。
- バンク25のBGMテーブル54項目と、未使用NULLの50番を除くSEテーブル55項目を各180フレーム実行し、ドライバーの停止や非有限の音声サンプルがないことを確認。項目数には停止・重複を含むため、曲数を意味しない。
- 各2〜6倍で、保存後60ホスト更新を再生し、復元後の映像と音声が完全一致。
- 旧ステートの読込、チェックサム破損の拒否と実行中ゲームの保持を確認。
- SDLの実経路で1〜6倍切替、保存・読込、メニュー表示を確認。Windows x64 Release／Android arm64 Debug APKのビルド成功。

ゲーム進行が速くなるため、BGM切替やSE要求の発生時刻自体は早くなる。映像の演出よりSEが長く続く場合もある。戦闘を含む全場面での聴感・SE優先順位、長時間の連続再生、Android実機での6倍速性能は未確認。テーブル検証は曲・SEの全尺やゲーム中の全条件の再現ではない。


## Androidの再生待機（0.2.2）

Androidでは音声を事前に蓄え、音声デバイスの消費量に合わせてホスト更新を進める。VSyncと別のフレーム時計を二重に待たず、通常再生で音声キューを破棄しない。待機はゲーム・描画処理を含む1フレーム分までに制限する。保存データとエミュレーターの速度・音声合成は変更しない。
定期SRAM保存は既存のAndroid SaveQueueへ非同期で渡し、SAFの処理完了をフレーム中に待たない。Insetsが同じならSurfaceや操作ボタンの再配置を行わない。Windowsの通常再生は従来の方式を維持する。
実機で報告された約15秒周期の停止の解消は未確認。確認結果と診断方法は `DEVELOPMENT.md` を参照。


## DQ3（0.3.0）

DQ3の標準版にも同じ音声専用コア方式で1〜6倍速を追加した。ROM固有の音声・入力接続と検証範囲は [dq3.md](dq3.md) を参照。DQ4の接続処理は維持する。
